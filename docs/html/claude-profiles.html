Claude Profiles

A Claude profile is a separate Claude Code config folder with its own login, settings and history. MultiTerminal lets each project name the profile it runs under, so work projects and personal projects stay apart, and it refuses to start a terminal rather than run a project under the wrong one.

Typical flow

  1. Create a folder for the second profile, for example C:\Users\you\.claude-work, and sign in to Claude Code there once.
  2. Add it in Settings → Claude Profiles with a name such as Work.
  3. Open Edit Project for each work project and choose Work under Claude profile.
  4. Launch as usual. Every terminal in that project's folder now runs under Work; everything else keeps using Default.

What a profile is, and why

Claude Code keeps everything about "you" in one config folder: who you are signed in as, your settings.json, installed plugins, your own skills and agents, and the history of every session. Normally that folder is %USERPROFILE%\.claude. Claude Code uses a different folder when the environment variable CLAUDE_CONFIG_DIR points at one.

A Claude profile in MultiTerminal is a name for one such folder. The usual reason to have two is to keep a work account and a personal account apart: different logins, different billing, different settings, and no shared history between them.

MultiTerminal sets the variable for you, per terminal, from the project the terminal belongs to. You do not set CLAUDE_CONFIG_DIR by hand for terminals MultiTerminal starts.

Setting up a second profile

A profile has to be signed in once before it is useful. There are two ways to do that.

Option A: outside MultiTerminal

  1. Create the folder, for example C:\Users\you\.claude-work.
  2. Open any terminal, point Claude Code at it, and start Claude: 
    $env:CLAUDE_CONFIG_DIR = 'C:\Users\you\.claude-work'
claude
  3. Sign in and answer the first-run questions. Then add the profile in Settings (next section).

Option B: inside MultiTerminal

  1. Create the folder (it must exist before it can be added).
  2. Add it in Settings → Claude Profiles.
  3. On a start screen choose Just Claude, pick a folder that no project owns, and choose the new profile under Claude profile. MultiTerminal notes that the profile has never been used and that Claude will ask you to sign in.
  4. Sign in and answer the first-run questions in that terminal.

A new profile starts from nothing. Expect Claude Code's onboarding, the "do you trust this folder" question for each folder, and permission prompts again, exactly as on a fresh machine. Nothing is copied from your Default profile.

Adding it in Settings

Open Settings and go to the Claude Profiles tab.

  • Default profile is shown at the top with its folder. It is built in and cannot be edited.
  • Under Additional profiles, click Add profile, type a Name and choose the Config folder (Browse… helps).
  • Remove takes a profile off the list. The folder itself is never deleted.

Saving checks every row and tells you which one is wrong. A profile needs:

  • a name that is not blank, not Default, and not used by another profile;
  • a folder given as a full path that already exists;
  • a folder that is not a drive root, not your user folder or anything above it, not the Default profile's folder, and not already used by another profile.

Profiles are a setting of this machine. If you remove or rename one that projects still use, MultiTerminal warns you first: those projects will refuse to start until you pick another profile for them.

Choosing a profile for a project

Open Edit Project and choose from the Claude profile list. Default means the project has no profile of its own.

A project remembers its profile by name. The name also travels with the project in its .claude\project.json, so the same project on another machine asks for the same profile name. If that machine has no profile with that name, the list shows it as (not configured on this machine) and the project will not launch there until you either add a profile with that name in Settings or choose another one for the project.

How a launch picks its profile

You never choose a profile for a terminal that belongs to a project. The project decides.

What you startProfile it runs under
A project (from its card, the project list, or a new project)That project's profile.
Any terminal in a project's folder, however it was opened: Just Claude, Open PowerShell, Launch as, a grid presetThe profile of the project that owns the folder.
A terminal in a subfolder of a project, or in one of its task worktreesThe profile of the nearest project at or above that folder.
A helper an agent spawnsThe profile of the project that owns the helper's folder. If no project owns it, the profile of the terminal that spawned it.
A terminal in a folder no project ownsDefault, unless you pick another one (below).

The Claude profile choice in Just Claude and Launch as appears only when it is a real choice: you have more than one profile, and the folder belongs to no project. For a folder a project owns, Just Claude shows that project's profile as fixed, and Launch as does not ask at all. To change it, change the project in Edit Project.

A plain PowerShell terminal gets the same profile as a Claude terminal would in that folder, so typing claude in it later lands in the right place. This applies to every terminal MultiTerminal starts, whatever command it runs.

After you restart MultiTerminal, a restored pane shows its start screen. Whatever you start from there is decided again by the rules above.

When MultiTerminal refuses to start

If a terminal's profile cannot be used, MultiTerminal does not start it and does not quietly use another profile instead. You get one message that begins Not started: and says what was being started, which project and profile were involved, and where to fix it. Helpers and background agents fail with the same explanation, reported back to whoever asked for them.

The message saysWhat it meansHow to fix it
The profile "is not configured on this machine" The project names a profile this machine does not have. Common after moving a project between machines, or after removing or renaming a profile. Add a profile with that name in Settings → Claude Profiles, or choose another profile for the project in Edit Project.
The profile "points at" a folder "which does not exist" The profile is on the list but its folder is gone (deleted, renamed, or on a drive that is not connected). Restore the folder, or correct the profile's folder in Settings.
The profile "has never been used on this machine" Only for launches nobody is watching: a spawned helper or a background agent. A profile that has never run Claude would stop at the sign-in and first-run questions, and nobody is there to answer them. Open a terminal under that profile yourself once and sign in, then try again. Terminals you open yourself are never refused for this reason; that is how a profile gets set up.
"The folder looks moved or copied" The folder's .claude\project.json says it is a project that MultiTerminal has registered at a different folder, and the two disagree about the profile. MultiTerminal will not guess which is right. If you moved the project, update its folder in Edit Project. If the folder is a copy, remove or correct the .claude\project.json inside it.
The folder "is registered to more than one project" with different profiles Two projects claim the same folder and are set to different profiles. Give both projects the same profile in Edit Project, or remove the duplicate project.
A profile "was chosen for it, but its folder belongs to project…" A profile was picked for a folder that a project owns, and it is not that project's profile. Start it without picking, or change the project's profile in Edit Project.
MultiTerminal "could not work out which Claude profile it belongs under" The project list could not be read at that moment. Try again. If it keeps happening, check the debug log.

These refusals apply to Codex terminals too. Codex itself does not use Claude profiles, but a project whose profile is broken does not start any terminal until the profile is fixed.

What is separate per profile

Everything Claude Code keeps in its config folder belongs to one profile only:

  • Login and account.
  • settings.json, including permissions and hooks you configured yourself.
  • Plugins you installed, and your own user-level skills and agents.
  • Sessions and transcripts. MultiTerminal's session history, token meter and resume lists read a project's sessions from that project's profile.
  • Agent teams. A team created under one profile is tracked separately from a team with the same name under another.
  • Memory that Claude Code and MultiTerminal keep per project folder.
  • First-run state: onboarding, folder trust, and permission prompts. A new profile asks all of these again.

You do not need to enable agent teams in each profile's settings. MultiTerminal switches them on for every terminal it starts.

The task board, projects, and the knowledge base are MultiTerminal's own and are not per profile. One board shows all your projects; each project simply runs under its own profile.

The MultiTerminal plugin

The MultiTerminal plugin (the hooks, skills and agents that connect a terminal to the board) is handed to Claude Code by MultiTerminal each time it starts a terminal. It does not need to be installed in each profile, and a brand-new profile gets it straight away.

Other plugins are different: they are installed per profile, so a plugin you rely on in Default has to be installed again in a second profile. See Plugin & Distribution for what the MultiTerminal plugin contains.

The Default profile

Default is what you had before profiles existed: Claude Code's normal folder, %USERPROFILE%\.claude. It is always there, cannot be renamed or removed, and is used by every project that has no profile of its own.

For a Default terminal MultiTerminal makes sure CLAUDE_CONFIG_DIR is not set, so Claude Code behaves exactly as it does when you run it by hand. This also means a value set in your PowerShell profile script cannot leak into a Default terminal and move it to another account without you noticing.

If MultiTerminal itself is started with CLAUDE_CONFIG_DIR set

Then that folder is your Default profile. MultiTerminal assumes you started it that way on purpose and keeps the value for Default terminals. The Claude Profiles tab shows the folder and notes that it came from MultiTerminal's own CLAUDE_CONFIG_DIR. The value is read once at startup; restart MultiTerminal after changing it.

What is not separated yet

Profiles currently separate what Claude Code stores and which account a terminal uses. Some of MultiTerminal's own features still span profiles. These are planned, not done:

  • Messaging between agents. An agent in one profile can still message, and see in the terminal list, an agent in another profile.
  • The shared pool. There is one pool for all terminals, not one per profile.
  • Session-memory search. Searching past sessions is not limited to the profile you are in.
  • The Oracle always runs under Default.

Until then, treat profiles as keeping accounts, settings and Claude Code's own history apart, not as a wall between agents that are running at the same time.

Installer: shared plugin location

The installer has a Plugin location page. The default installs the MultiTerminal plugin into your Default profile, as earlier versions did. If you use more than one profile, choose Shared location instead: one copy is installed outside every profile, and MultiTerminal terminals use it whichever profile they run under. An upgrade keeps whichever choice you made before.

An optional further page can make the plugin marketplace known to other profiles, for plain claude sessions started outside MultiTerminal. That adds the marketplace only; it does not install or enable the plugin there. MultiTerminal's own terminals do not need it.
